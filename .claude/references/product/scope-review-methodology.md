# Scope Review Methodology

Challenge assumptions about WHAT to build and how much, before design work begins.

## Four Scope Modes

| Mode | Question | When to Use | Risk |
|------|----------|-------------|------|
| **EXPAND** | "What's the 10x version?" | Greenfield, exploring possibilities | Scope creep, analysis paralysis |
| **SELECTIVE EXPAND** | "Keep core, add one high-leverage extension" | Feature iteration, v2 planning | Gold-plating one dimension |
| **HOLD** | "Is current scope right-sized?" | Mid-project validation, milestone reviews | Confirmation bias |
| **REDUCE** | "What's the minimum that tests the hypothesis?" | MVP, tight deadline, uncertain market | Cutting too deep, losing value |

## Cognitive Models

| Model | Application |
|-------|-------------|
| Inversion (Munger) | "What would make this fail?" — remove those risks |
| Regret Minimization (Bezos) | "Will I regret NOT doing this in 5 years?" |
| Second-Order Effects | "If we ship X, what does that enable/break?" |
| 10x Thinking | "What would this look like at 10x scale?" |

## Process

1. **State** the current scope in one sentence
2. **Identify assumptions** — market, technical, resource, timeline
3. **Apply each mode** — generate concrete options per mode
4. **Evaluate** options against constraints (time, team, risk appetite)
5. **Recommend** a mode with reasoning

## Distinction from /j-brainstorm

- **scope-review** = WHAT to build (challenge the boundary)
- **/j-brainstorm** = HOW to build it (design within the boundary)
- Scope review can precede brainstorm: "Are we building the right thing?" then "How do we build it?"

## Anti-Patterns

- Expanding scope without new evidence supporting it
- Reducing scope to avoid hard problems (vs genuinely tight constraints)
- Skipping HOLD — sometimes the current plan is correct
- Scope review as procrastination — time-box to 15-30 min
